# Переводы и AI-assisted workflow

## Назначение

Этот документ фиксирует целевую модель переводов uDream и безопасный порядок экспериментов с API-переводом. Он не означает, что новые переводы уже созданы или что активная база должна быть немедленно изменена.

## Целевой набор данных

После завершения D1 проект стремится иметь следующие логически независимые наборы:

1. **Исходная база** — канонический набор на языке исходного материала, без русской переводческой редакции.
2. **Текущий русский перевод** — опубликованный и проверенный вариант, который сейчас используется приложением.
3. **Альтернативный русский перевод A** — отдельный вариант для сравнения качества и формулировок.
4. **Альтернативный русский перевод B** — второй независимый вариант, если его удастся получить и проверить с достаточным качеством.

Это целевая модель, а не требование искусственно создавать лишние копии. Если надёжно получается только один русский перевод, проект сохраняет одну русскую версию и исходную базу. Количество вариантов не должно быть важнее качества, происхождения и проверяемости.

## Как поступить с текущими эквивалентными сериализациями

D1.1 исправил прежнюю классификацию `data/bd2.json` и `data/db.json`.

Файлы не являются точными байтовыми дубликатами: у них разные размеры и raw SHA-256. После JSON-разбора и canonical normalization все 4 086 записей, порядок, поля и значения совпадают. Это две физические сериализации одного логического английского набора.

До завершения D1.2 оба файла сохраняются без изменений.

Во время D1.2 необходимо:

1. утвердить один логический dataset ID;
2. определить канонический путь с учётом Git-истории и существующих ссылок;
3. сохранить оба raw hash и общий canonical hash;
4. проверить maintained и archived ссылки на оба имени;
5. создать запись миграции и способ восстановления;
6. только после отдельного утверждения убрать лишнюю физическую сериализацию из поддерживаемой структуры.

Эквивалентная сериализация не считается самостоятельным переводом или редакцией. Полное доказательство, hashes и рекомендация находятся в `docs/DATA_PROVENANCE.md`.

## Идентичность каждого варианта

Каждый самостоятельный набор или перевод должен иметь собственный стабильный идентификатор и метаданные:

- источник и книга;
- исходный язык;
- язык перевода;
- название варианта;
- версия или дата;
- исходный commit или SHA-256;
- способ получения;
- переводчик, инструмент или модель;
- шаблон инструкции для преобразования;
- правила редакторской обработки;
- результаты автоматической проверки;
- статус человеческой проверки;
- связь с предыдущей версией.

Пример логических идентификаторов, которые ещё должны быть утверждены D1:

```text
source-divinity-code-en
ru-current-v1
ru-deepseek-candidate-v1
ru-alternative-reviewed-v1
```

Имена файлов и каталогов нельзя окончательно утверждать до завершения реестра D1.2.

## Использование DeepSeek API

DeepSeek рассматривается как один из возможных инструментов для создания дополнительного кандидата перевода или расширения непереведённых полей. Результат API не считается автоматически правильным, опубликованным или богословски проверенным.

### Где допускается запуск

Перевод через API выполняется только:

- локальным служебным скриптом разработчика; или
- отдельным GitHub Actions workflow с ключом в GitHub Secrets.

Статический сайт и установленная PWA не должны обращаться к переводческому API напрямую. Встраивание ключа в браузерный JavaScript неизбежно раскроет его пользователям.

### Хранение ключа

Ключ API:

- не записывается в Git;
- не помещается в `index.html`, `script.js`, `src/`, JSON-базы, патчноуты или документацию;
- локально передаётся через переменную окружения или игнорируемый `.env`;
- в GitHub Actions хранится только как encrypted secret;
- не выводится в логи, отчёты об ошибках и артефакты;
- при подозрении на утечку немедленно отзывается и заменяется.

Рекомендуемое имя локальной переменной:

```text
DEEPSEEK_API_KEY
```

В репозиторий может быть добавлен только безопасный `.env.example` без значения.

## Безопасный конвейер AI-перевода

Экспериментальный перевод должен идти отдельными контролируемыми шагами:

1. выбрать точную исходную версию и зафиксировать её hash;
2. определить поля, которые разрешено переводить;
3. запретить модели изменять ID, источники и библейские ссылки;
4. обрабатывать данные небольшими возобновляемыми пакетами;
5. сохранять сырой ответ отдельно от нормализованного кандидата;
6. записывать модель, дату, параметры и версию prompt-шаблона;
7. повторно проверять число записей, ID, типы полей и ссылки;
8. формировать отчёт различий с текущим переводом;
9. проводить человеческую выборочную и содержательную проверку;
10. публиковать только через отдельный data-релиз после утверждения.

Сбой посередине не должен портить уже опубликованный файл. Скрипт обязан поддерживать checkpoint и продолжение с последнего подтверждённого пакета.

## Что нельзя поручать модели без проверки

AI-перевод нельзя автоматически использовать для:

- добавления новых библейских ссылок;
- усиления или изменения смысла толкования;
- объединения разных книг в одну запись;
- удаления неоднозначных мест;
- замены источника;
- изменения стабильного ID;
- принятия решения, какой перевод является окончательным.

Такие изменения требуют сверки с исходником и отдельного редакторского решения.

## Сравнение вариантов

Будущий интерфейс может позволить:

- выбрать исходную базу;
- выбрать текущий или альтернативный перевод;
- открыть два варианта рядом;
- выполнить объединённый поиск с явной подписью источника и варианта.

Переключатель не реализуется до утверждения реестра наборов, правил ID и миграционного плана. Активная база `data/divinity_code_ru.json` остаётся единственным опубликованным runtime-набором до отдельного функционального релиза.

## Критерии допуска нового перевода

Новый вариант можно считать кандидатом на публикацию только когда:

- сохранён исходный набор и его hash;
- создана отдельная версия, не перезаписывающая текущую;
- число и идентичность записей объяснены;
- автоматические проверки прошли;
- сформирован отчёт различий;
- спорные формулировки и ссылки проверены человеком;
- права и происхождение данных не стали менее ясными;
- существует точный откат;
- изменение оформлено отдельным Pull Request, data-релизом и uNews-патчноутом.

## Решение, которое должен принять D1

D1 должен дать однозначный ответ на четыре вопроса:

1. какой файл является канонической исходной базой;
2. какой вариант является текущим опубликованным русским переводом;
3. нужны ли два альтернативных перевода и как они будут отличаться;
4. можно ли безопасно удалить лишнюю физическую сериализацию после сохранения истории и миграционной записи.

До этого решения существующие данные не удаляются и не переименовываются.
