# Реальные скриншоты для патчноутов и uNews

## Цель

Каждый новый патчноут uDream должен использовать новое реальное изображение, относящееся именно к фактически выполненному изменению.

Для пользовательских изменений основной способ — автоматический снимок настоящего браузера Chromium через Playwright. Для документационных изменений допускается реальный снимок GitHub-страницы, отчёта Actions или локально отрендеренного актуального документа.

## Что считается реальным скриншотом

Подходит изображение, которое:

- создано браузером из точного commit или рабочей ветки;
- показывает фактический интерфейс, документ, Release, Pull Request или результат проверки;
- соответствует версии и функции патчноута;
- не было взято из старого патча;
- не скрывает ошибку, пустое состояние или старый кеш;
- имеет записанные источник, цель, commit и время захвата.

Не подходит:

- старая картинка ради обязательного поля `image`;
- изображение другой функции или другой версии;
- вручную нарисованная схема, выдаваемая за снимок сайта;
- AI-изображение вместо подтверждения реальной функции;
- скриншот, на котором не видно заявленного результата;
- снимок с токенами, ключами, приватными данными или локальными путями пользователя.

## Почему Playwright

Playwright запускает настоящий Chromium и может:

- поднять локальный сайт из точного checkout;
- задать desktop или mobile viewport;
- очистить storage и Service Worker состояние;
- дождаться загрузки базы;
- заполнить поиск;
- нажать элемент;
- проверить видимый текст;
- сохранить PNG всей страницы или конкретного блока.

Внешний платный screenshot-сервис для основной цепочки не требуется. Он может рассматриваться только как аварийный резерв после отдельной проверки приватности, стабильности и стоимости.

Точный набор файлов может быть скорректирован при реализации, но архитектура должна оставаться отдельной от runtime приложения.

## Канонический процесс захвата

```text
branch / Pull Request
    ↓
GitHub Actions checkout точного commit
    ↓
локальный HTTP-сервер
    ↓
Playwright Chromium
    ↓
проверка ожидаемого состояния
    ↓
PNG desktop + mobile
    ↓
workflow artifact
    ↓
просмотр человеком или агентом
    ↓
одобренный PNG добавляется в news/
    ↓
патчноут проходит валидатор
    ↓
merge делает запись доступной uNews
```

## Почему изображение не коммитится сразу в main

Автоматический браузер может получить:

- временную ошибку загрузки;
- пустую карточку;
- неверный viewport;
- старое состояние service worker;
- неожиданное модальное окно;
- неправильный текст из-за изменения данных.

Поэтому workflow сначала создаёт artifact. Изображение добавляется в branch только после проверки, а в `main` попадает исключительно через Pull Request.

## Обязательные сценарии

### Пользовательская функция

Сценарий должен:

1. открыть точную страницу;
2. очистить только данные, которые могут исказить проверку;
3. дождаться загрузки приложения;
4. выполнить действие пользователя;
5. проверить ожидаемый текст или элемент;
6. сделать снимок области, где видно результат.

### PWA и кеш

Для изменений Service Worker требуется отдельная проверка:

- первый запуск;
- повторный запуск;
- обновление со старого кеша;
- сохранение безопасных пользовательских настроек;
- offline fallback после успешной установки;
- отсутствие удаления чужих origin caches.

Такая проверка не считается выполненной только по обычному desktop-скриншоту.

### Документационный патч

Допускается снимок:

- актуального `WORK_STATUS.md`;
- GitHub Release;
- Pull Request с точным списком файлов;
- успешного GitHub Actions run;
- реального отрендеренного документа из точного branch commit.

Изображение должно честно называться документальным снимком, а не демонстрацией функции приложения.

## Метаданные патчноута

Для каждого нового патчноута должны добавляться поля:

```yaml
image: 2026-07-22-udream-example.png
image_source: playwright
image_target: scenario/search-water
image_commit: abc1234
image_captured_at: 2026-07-22T07:30:00Z
```

Допустимые `image_source`:

- `playwright` — автоматический Chromium;
- `manual-browser` — ручной снимок реального браузера;
- `github-ui` — реальный снимок GitHub Issue, PR, Release или Actions;
- `document-render` — снимок актуального документа, отрендеренного из точного commit.

`image_target` должен называть URL, сценарий или документ. `image_commit` должен указывать commit, который был показан. `image_captured_at` хранится в UTC.

## Проверки Pull Request

Автоматический валидатор должен требовать для нового патчноута:

- новый Markdown-файл;
- новый PNG или JPEG в том же PR;
- отсутствие повторного использования существующего изображения;
- обязательные screenshot metadata;
- корректную сигнатуру PNG/JPEG;
- отсутствие секретоподобного текста в патчноуте;
- соответствие `project: uDream` и `series: udream`.

Валидатор не может доказать содержательную правдивость изображения. Поэтому перед merge остаётся визуальная проверка человеком или ответственным агентом.

## Имена файлов

Рекомендуемый формат:

```text
YYYY-MM-DD-udream-vVERSION-short-scenario.png
```

Примеры:

```text
2026-07-22-udream-v23-8-6-work-status.png
2026-07-22-udream-v23-9-0-search-water-mobile.png
```

## Desktop и mobile

Для заметного изменения интерфейса предпочтительно создавать два artifact-файла:

- desktop: примерно `1440×1000`;
- mobile: примерно `390×844`.

В патчноут попадает наиболее понятный основной кадр. Второй может быть включён в `images` как альбом или сохранён как проверочный artifact.

## Секреты и приватность

Перед снимком необходимо:

- использовать тестовые или публичные данные;
- закрыть приватные вкладки и панели;
- не отображать environment variables;
- не выводить GitHub Secrets;
- не показывать локальные домашние пути;
- не включать email, токены, cookies и приватные Issue;
- очищать test artifacts от случайных данных.

## Ответственность uNews

uNews публикует файл, указанный в патчноуте. Он не должен самостоятельно подменять, генерировать или выбирать другую картинку.

Если изображение неверно до публикации, исправляется самый ранний непубликованный патчноут проекта. Если неверное изображение уже опубликовано, используется документированная команда обслуживания uNews по известному `message_id`, а не новый дублирующий пост.

## Граница текущего патча

Документационный baseline `23.8.6` вводит правила и проверки метаданных. Полная автоматическая установка Playwright, сценарии и workflow artifacts выполняются отдельным патчем `23.8.7` до начала D1.1.
