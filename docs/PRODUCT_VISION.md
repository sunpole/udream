# Видение продукта uDream

## Миссия

uDream превращает трудоёмкий ручной поиск по христианской литературе о снах и видениях в быстрый, понятный и проверяемый мобильный справочник.

Проект должен помогать пользователю:

- найти символ, синоним или связанную тему;
- увидеть толкование и его источник;
- различать материалы разных книг и редакций;
- возвращаться к просмотренным карточкам;
- пользоваться справочником как сайтом и установленной PWA;
- сохранять доступ к проверенным прежним версиям проекта.

uDream является поисковым интерфейсом к источникам, а не заменой исходных книг и не официальным изданием их содержания.

## Для кого создаётся продукт

Основной сценарий — человек открывает uDream на телефоне, вводит слово из сна и быстро получает подходящие карточки без просмотра больших PDF-файлов.

Дополнительные сценарии:

- изучение связанных символов и библейских ссылок;
- сравнение толкований из разных источников;
- повторное открытие карточек из локальной истории;
- работа без постоянного соединения после установки PWA;
- подготовка и проверка новых вариантов базы без разрушения опубликованной версии.

## Конечный образ продукта

Завершённый uDream должен включать:

1. быстрый и предсказуемый поиск по символам, алиасам, описаниям и тегам;
2. понятное указание источника каждого толкования;
3. поддержку двух исходных книг без смешивания происхождения текста;
4. безопасный выбор отдельной базы, варианта перевода или согласованного объединённого поиска;
5. мобильный, доступный и устанавливаемый интерфейс;
6. документированный процесс подготовки, перевода, проверки и публикации данных;
7. административный процесс, который не подвергает риску публичную базу;
8. неизменяемые релизы и понятный откат;
9. автоматические тесты данных, поиска, PWA и запуска приложения;
10. прозрачные правила прав, происхождения и использования сторонних материалов.

## Текущее состояние

Стабильная версия `v23.8.0` уже предоставляет:

- активную базу из 4 086 записей;

## Обязательная стратегия данных

### Никаких разрушительных замен

Ни одна исходная база, редакция или версия перевода не должна молча перезаписывать другую.

Для каждой базы или редакции должны сохраняться:

- собственный файл или каталог;
- стабильный идентификатор набора данных;
- название источника;
- язык;
- версия или дата;
- способ получения;
- инструмент и правила преобразования;
- связь с исходным материалом;
- результаты проверки.

### Сохранение вариантов перевода

Если создаётся новый вариант перевода, прежний вариант сохраняется. Новый перевод получает отдельную версию и описание отличий.

Запрещено:

- массово менять опубликованный перевод без отдельного data-релиза;
- смешивать исходный текст, перевод и редакторские дополнения без маркировки;
- удалять старый вариант только потому, что появился более новый;
- менять стабильные ID без документированной миграции.

### Целевая модель переводов

После завершения D1 проект стремится иметь:

1. одну каноническую исходную базу на языке источника;
2. один текущий опубликованный русский перевод;
3. до двух самостоятельных альтернативных русских переводов для сравнения качества.

Два одинаковых файла не считаются двумя переводами. Если текущая пара действительно является точным дублем, после доказанной безопасной миграции должен остаться один канонический файл, а история прежнего дубликата — в Git и миграционной записи.

Если два качественно независимых альтернативных перевода получить не удастся, проект не создаёт искусственные варианты ради количества. В таком случае сохраняются исходная база и один надёжный русский перевод.

Подробный порядок зафиксирован в [документе о переводах и AI-assisted workflow](TRANSLATION_WORKFLOW.md).

### DeepSeek как вспомогательный инструмент

DeepSeek API может использоваться только для создания отдельного кандидата перевода или расширения непереведённых полей. Результат модели не считается автоматически правильным, опубликованным или богословски проверенным.

Ключ API не должен попадать в браузерный код, JSON-базы, Git, патчноуты или логи. Перевод запускается локальным служебным скриптом либо GitHub Actions с encrypted secret. Каждый запуск создаёт новую кандидатную версию и не перезаписывает активную базу.

### Две исходные книги

До утверждения продуктовой модели данные двух книг должны оставаться различимыми по происхождению.

Будущая реализация может поддерживать:

- поиск только по одной книге;
- поиск по выбранной редакции или переводу;
- объединённый поиск с обязательным указанием источника;
- сравнение нескольких карточек по одному символу.

Объединённая база не должна уничтожать отдельные исходные наборы.

## Технические принципы

- GitHub `main` — источник опубликованного сайта.
- Git-теги и GitHub Releases — неизменяемые точки восстановления.
- Проект остаётся статическим и совместимым с GitHub Pages, пока реальная задача не потребует backend.
- JavaScript ES Modules, JSDoc и `@ts-check` остаются основой; TypeScript вводится только при доказанной пользе.
- Изменения интерфейса, данных, PWA и архитектуры выполняются отдельными контролируемыми этапами.
- Активная база не меняется в PR, цель которого относится только к интерфейсу или документации.
- Исторические каталоги, исходные PDF и сохранённые версии не удаляются как обычная очистка.
- Секреты и персональные данные не хранятся в репозитории.
- Любое утверждение о проверке должно соответствовать реально выполненной проверке.

## Критерии готовности следующего этапа

Перед началом следующей функциональной серии должны быть выполнены следующие условия:

- документация не противоречит текущему runtime;
- текущий релиз и точный SHA записаны одинаково во всех документах;
- открытые задачи разделены на завершённое, следующий этап и более поздний backlog;
- определена граница следующего этапа;
- сохранена точка безопасного отката;
- изменения следующего этапа не смешивают документацию, данные и новый интерфейс без необходимости.

После документационного обновления `23.8.4` эти условия считаются выполненными.

## Следующий этап

Следующая рекомендуемая серия — **D1: происхождение данных и архитектура нескольких наборов**.

D1 не должен сразу менять тексты активной базы. Его первая часть должна:

1. восстановить известный процесс создания `data/divinity_code_ru.json`;
2. описать происхождение и различия текущих файлов данных;
3. определить реестр наборов данных и вариантов перевода;
4. установить канонический исходный файл и судьбу точного дубликата;
5. спроектировать безопасный выбор источника и объединённый поиск;
6. определить проверки ссылок, ID, дублей и подозрительных записей;
7. подготовить воспроизводимый AI-assisted перевод с безопасным хранением ключа;
8. подготовить план миграции без разрушения текущих 4 086 записей.

Только после отдельного утверждения архитектуры D1 допускаются изменения структуры данных или пользовательского переключателя баз.

## Что не считается завершённым

Следующие направления остаются будущей работой и не должны ошибочно описываться как готовые:

- восстановленный и воспроизводимый pipeline перевода активной базы;
- альтернативные русские переводы;
- полная содержательная проверка всех 4 086 записей;
- подтверждённые URL и формулировки разрешений для каждого PDF;
- пользовательский выбор между двумя книгами и вариантами перевода;
- восстановленный административный редактор;
- полный accessibility-аудит;
- автоматические браузерные smoke-тесты;
- итоговый аудит приватности и sharing.
