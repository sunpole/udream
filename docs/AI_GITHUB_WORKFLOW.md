# Единая работа ИИ, GitHub, чатов и устройств

## Назначение

Этот документ определяет один рабочий процесс для uDream независимо от количества устройств, чатов ChatGPT, Codex-сессий или других ИИ-агентов.

Главный принцип:

> Чат помогает выполнять работу, но не хранит официальное состояние проекта. Официальное состояние всегда восстанавливается из GitHub.

## Иерархия источников истины

При расхождении сведений используется следующий порядок:

1. фактическое состояние GitHub: `main`, открытые Pull Request, branches, commits, tags, Releases и результаты Actions;
2. `WORK_STATUS.md` — текущая активная задача, ветка, прогресс, пауза и следующий точный шаг;
3. активный GitHub Issue — подробное техническое задание утверждённого этапа;
4. Pull Request — фактический diff, проверки, риски и публикационный материал конкретного изменения;
5. поддерживаемая документация: `VERSION.md`, `ROADMAP.md`, `docs/PROJECT_STATE.md` и специализированные документы;
6. сообщения текущего чата;
7. старые чаты, память ИИ и локальные заметки.

Старый чат никогда не может отменить более новый commit, Pull Request или `WORK_STATUS.md`.

## Стандарт старта на любом устройстве

Перед любыми изменениями человек или агент обязан:

```bash
git switch main
git pull --ff-only origin main
cat WORK_STATUS.md
```

Затем проверить:

```bash
git status --short --branch
git log -5 --oneline
gh pr list --state open
```

После этого:

- при `READY` начинается только следующая утверждённая работа;
- при `IN_PROGRESS` продолжается указанная ветка и задача;
- при `PAUSED` продолжается точный следующий шаг;
- при `BLOCKED` сначала устраняется записанный блокер;
- конкурирующая ветка для той же цели не создаётся без явного решения владельца.

## Обязательная блокировка активной работы

`WORK_STATUS.md` выполняет роль мягкой блокировки проекта.

До первого изменения в задаче в него записываются:

- статус `IN_PROGRESS`;
- дата и среда;
- точная ветка;
- одна основная цель;
- планируемые файлы;
- критерии завершения;
- первый точный шаг.

Изменение `WORK_STATUS.md` должно быть отправлено в GitHub. Локальный незапушенный статус не защищает от параллельной работы другого чата.

## Разделение ролей

### ИИ выполняет самостоятельно

Когда доступны необходимые инструменты, ИИ должен самостоятельно:

- читать GitHub-факты и документацию;
- создавать рабочую ветку;
- обновлять `WORK_STATUS.md`;
- изменять код и документацию;
- запускать доступные проверки;
- создавать commits и Pull Request;
- проверять список файлов и GitHub Actions;
- исправлять обнаруженные ошибки;
- готовить патчноут и реальные скриншоты;
- обновлять handoff после merge.

ИИ не должен перекладывать на владельца команды, которые способен безопасно выполнить через подключённый GitHub.

### Владелец подключается только там, где нужен человек

Участие владельца требуется для:

- решения о продуктовой цели, дизайне или содержательном смысле;
- предоставления секрета через безопасное хранилище без передачи значения в чат;
- проверки на физическом устройстве, которого нет у агента;
- богословской, переводческой или редакторской оценки содержимого;
- подтверждения спорного изображения или публичного текста;
- действий, для которых подключённые инструменты не имеют разрешения.

## Одна задача — одна ветка — один PR

Одна ветка должна иметь одну основную цель. Нельзя объединять без отдельного утверждения:

- изменение данных;
- редизайн интерфейса;
- архитектурную миграцию;
- изменение PWA;
- массовый перевод.

Название ветки должно объяснять задачу и версию, например:

```text
ops/unified-ai-workflow-v23.8.6
feat/example-v23.9.0
docs/data-provenance-d1.1
```

## Переход между чатами

Новый чат не требует пересказа всей истории. Достаточно запроса:

```text
Открой sunpole/udream. Сначала проверь main, открытые PR, последние commits и WORK_STATUS.md. Продолжай только указанную там активную задачу. Старый контекст чата не считай источником истины.
```

После чтения GitHub новый агент обязан своими словами назвать:

- текущий статус;
- активную ветку;
- активный PR;
- последнюю завершённую работу;
- следующий точный шаг;
- запреты текущего этапа.

Только после этого разрешены изменения.

## Фиксация паузы

Перед остановкой незавершённой работы:

1. сохранить фактические изменения в commit;
2. отправить branch в GitHub;
3. выставить `PAUSED` или `BLOCKED`;
4. перечислить завершённое и незавершённое;
5. указать последний проверенный commit;
6. записать один точный следующий шаг;
7. указать, что нельзя делать при продолжении.

Фраза «продолжить позже» без commit и push не является handoff.

## Завершение и merge

Перед merge:

- статус становится `COMPLETED`;
- записываются фактические файлы и проверки;
- PR содержит полный scope и риски;
- GitHub Actions проходят;
- пользователь видит точный публичный текст и реальное изображение uNews;
- никакие запланированные, но невыполненные пункты не называются завершёнными.

После merge отдельным коротким обновлением:

- `WORK_STATUS.md` возвращается в `READY`;
- указывается merge commit;
- удалённая рабочая ветка закрывается;
- записывается следующая утверждённая задача.

## Конфликт или устаревшая информация

Если `WORK_STATUS.md` противоречит реальным PR или commits:

1. изменения и merge временно прекращаются;
2. фиксируются реальные GitHub-факты;
3. `WORK_STATUS.md` исправляется первым;
4. только затем продолжается работа.

Если старый Issue содержит старый SHA или baseline, его обновляют или добавляют заметное уточнение. Issue хранит задание, а не живое состояние.

## Запреты

Нельзя:

- начинать новую крупную задачу при незакрытом `IN_PROGRESS`, `PAUSED` или `BLOCKED`;
- считать локальную ветку доступной другим устройствам до push;
- утверждать проверку телефона, PWA или offline без реального выполнения;
- использовать старую картинку для нового патчноута;
- создавать новый перевод поверх предыдущего файла;
- передавать API-ключ в чат, frontend, JSON, commit, лог или скриншот;
- перемещать опубликованный tag;
- принимать память ИИ за доказательство выполнения.

## Минимальный итог каждого ответа о выполненной работе

Отчёт должен содержать:

- что фактически сделано;
- branch, PR и commit;
- изменённые файлы;
- выполненные проверки;
- что не проверено;
- публичный текст и изображение, если они пойдут в uNews;
- следующий точный шаг по `WORK_STATUS.md`.
